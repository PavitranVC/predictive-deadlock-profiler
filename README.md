# Predictive Deadlock Profiler (PDP)

**We predict lock-order deadlocks from one run, confirm them, and measure how Linux scheduling decides whether they ever show up.**
PDP is an `LD_PRELOAD` library (`libpdp.so`) that records every `pthread_mutex_*` and `sem_*` call of an unmodified C program, an analyzer that builds a lock-order graph from that log and finds cycles (potential deadlocks) even when the run did not hang, a confirmer that re-runs the program with targeted delays to show the deadlock is real, and an experiment harness that measures how often the same bug manifests under different Linux scheduling policies, core counts and load. Predict-and-confirm is prior art (GoodLock 2000, DeadlockFuzzer PLDI 2009, Helgrind, ThreadSanitizer, Linux lockdep, ICSE 2020, PLDI 2023); our contribution is the scheduling study. Course project for an Operating Systems class, built with gcc on Linux (WSL2).

## Quick start

Needs gcc, make and python3. The Stage 6 demo also uses gdb (`sudo apt install gdb`), and the experiment uses `taskset` and `chrt` (both in util-linux).

```
make                                   # builds build/libpdp.so, build/pdp, build/pdp-analyze and tests/bin/*
make test                              # ground-truth suite: predictions and hang checks on known programs

# The bank example: a lock-order bug that a clean run does not show.
build/pdp run -o bank.log tests/bin/bank seq              # 1. record a clean run (it never hangs)
build/pdp analyze bank.log                                # 2. predict: reports the A->B / B->A cycle and a fix
build/pdp confirm --log bank.log --baseline -n 10 \
    ./tests/bin/bank race 1                               # 3. confirm: runs with a delay, watchdog reports real hangs

scripts/demo.sh                                           # the live walkthrough (DEMO_NOPAUSE=1 runs it straight through)
```

The experiment runs the real deadlock programs natively (no PDP) and counts hangs:

```
RUNS=5 OUT_DIR=$(mktemp -d) scripts/run_experiment.sh     # smoke test; never write a smoke test into results/
sudo -E scripts/run_experiment.sh                         # full run (10,800 runs, takes hours; files end up owned by root)
python3 scripts/plot.py                                   # hang-rate charts and summary (needs matplotlib)
```

The full run needs root for the real-time policies (`chrt -f` / `chrt -r`). Without root the script tries `sudo -n`, and
if that fails it skips the FIFO and RR cells with a warning, so `results/` would then hold only the `default` scheduler.
The script also refuses to run the RT configs if `sched_rt_runtime_us` is `-1`, because a spinning real-time thread
could then freeze the machine. All scripts refuse to overwrite an existing CSV unless `FORCE=1` is set.

## Headline results

Two machines ran the same 10,800-run matrix (3 binaries x 3 schedulers x 3 core sets x 2 loads x 200 runs, 95% Wilson
intervals). **The primary result is WSL2**, on a laptop with an Intel Core Ultra 9 275HX, the course platform
(`results/wsl2/`). **The cloud VM (4 vCPUs) is the replication** (`results/`). Full tables and caveats are in
`docs/stages/stage-5.md`.

Findings that replicated on both platforms:

- **One core never shows the bug.** 0 of 200 runs hung in all 18 one-core cells on WSL2, and in all 18 on the cloud VM.
- **The default scheduler with load hides the bug on two cores.** bank: 67.0% hung idle on WSL2, 0.5% with one
  stress-ng worker per core (cloud: 64.0% to 0.5%).
- **Real-time scheduling with the same load exposes it.** Under `SCHED_FIFO` and `SCHED_RR`, bank and sem_sq hang in
  99.0% to 100.0% of loaded runs in all 16 cells with two or four cores, on both platforms. Bank on two cores under
  FIFO goes from 62.0% idle to 100.0% loaded on WSL2 (cloud: 75.0% to 100.0%).
- **Helgrind is wrong twice, on both platforms.** It flags the gate case (a false positive) and misses the semaphore
  cycle in sem_sq. PDP reports the three real cycles and filters the gate case.

**Differences, observed and not explained:** the four-core idle rates for bank and sem_sq are 57 to 68% on WSL2 against
about 94% on the cloud, and philo_naive on two real-time cores hangs in 0.5 to 2% of WSL2 runs against 43.5 to 72.5% on
the cloud. The candidate causes are hypotheses (`docs/stages/stage-5.md`).

**Cost:** PDP adds 1.5 to 3.1 microseconds per lock operation on WSL2 (6.7 to 11.3 on the cloud). That is a 12x to 33x
wall-time slowdown on lock-only microbenchmarks (18x to 141x on the cloud). The main cost is one `write()` per event;
per-thread buffers are the planned fix.

## Prior art

- **GoodLock** (Havelund and Visser, 2000): the lock-order graph and cycle idea that most later tools build on.
- **DeadlockFuzzer** (Joshi, Park, Sen, Naik; PLDI 2009): predicts from a trace, then steers the scheduler at the cycle's statements to make the deadlock happen. This is predict-and-confirm.
- **Helgrind** (Valgrind): a lock-order and race checker run under emulation. Our baseline.
- **ThreadSanitizer** (Google): a compiler-instrumented race and lock-order checker.
- **Linux lockdep**: the kernel's lock dependency validator, which checks lock order at run time.
- **ICSE 2020**, "Low Overhead Deadlock Prediction": a prediction technique aimed at low run-time cost.
- **PLDI 2023**, "Sound Dynamic Deadlock Prediction in Linear Time": prediction with soundness and linear-time analysis.

We do not claim predict-and-confirm as a new method. Our contribution is the scheduling study: a measured answer, with
confidence intervals, to how often a real deadlock shows up natively under different schedulers, core counts and loads.

## Known limits

- **Static and setuid binaries ignore `LD_PRELOAD`**, so PDP cannot see them.
- **Mutexes and semaphores only.** `pthread_cond_wait`, timed locks and other synchronisation are not modelled. Semaphores use a binary-semaphore model with no true owner.
- **`fork()` is not handled.** A forked child runs without the watchdog.
- **A confirmed deadlock is evidence, not proof.** One run that deadlocks shows the cycle can happen under the delay. Zero of N without the delay does not show it never does.
- **Overhead is high for lock-heavy code.** The 1.5 to 11 microseconds per operation (WSL2 to cloud) is measured on microbenchmarks only.
- **Two machines, two confounds.** The WSL2 run (primary) used randomised block order and `stress-ng` load. The cloud run (replication) used a fixed run order and bash busy-loop load, so the machine and the load generator both differ between the two (see `docs/stages/stage-5.md`). WSL2 is itself a virtual machine, and its vCPUs are not physical cores.

## Future work

- A launcher that does not depend on `pdp run` (pipe, fork and exec handling), and `fork()` support.
- Runtime enforcement of the suggested lock order, not only advice.
- Read-write locks and condition variables in the model.
- eBPF or futex tracing, to measure the kernel side without an interceptor.
- A benchmark generator for random lock-order programs.
- CI/CD, so `make test` and the smoke experiment run on every push.
- Per-thread log buffers, to remove the write syscall from the lock path.
